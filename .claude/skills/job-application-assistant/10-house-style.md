# House Style Spec (match exactly on every resume and cover letter)

<!-- This is the single home for formatting rules. Everything here is a default you can change once, in one place. -->

Every tailored document must look identical to every other one the user sends out. Generate the `.docx` with docx-js via a Node script. Exact spec:

- **Font:** Times New Roman throughout.

- **Sizes:** name 20pt; section headers 12pt; body, bullets, and role lines 11pt. Same body size everywhere.

- **Section headers:** ALL CAPS, 12pt, not bold, with a thin black bottom rule (border bottom, single, size 4 eighths-pt, space 1).

- **Header (centered):** name 20pt not bold, **centered**. Contact line directly under it, 11pt, also **centered**, separated by `  //  ` (LinkedIn and GitHub as links). Both lines use `jc=center`. **The contact line reads `<City, ST>  //  <email>  //  <phone>  //  <linkedin>  //  <github>`, with the fields taken from the candidate profile. Fix the order once, then never vary it between documents.**

- **Education layout (exact):** line 1 = university (**bold; the location stays regular weight, not bold**) with location right-aligned via tab. Line 2 = degree with the expected graduation date right-aligned via tab on the **same line**. Line 3 = `GPA: X.XX/4.0` italic on its own line, taken from the candidate profile. **When a builder script is copied from an older application, recheck the GPA line before rendering; an old script can carry a superseded figure, and old scripts are otherwise left alone so their rendered PDFs still match the hashes recorded in the tracker.** **Relevant-coursework line:** omit by default; include a short, role-relevant line only when it is really necessary (e.g., a finance or quant role where the user lacks direct experience and the coursework supplies a needed signal). When included, it is plain black body text, never gray. **Never put per-class letter grades (e.g., "(A)") next to course names in the coursework line, and never list individual class grades anywhere in the resume or cover letter. Only the cumulative GPA is shown.** List courses by name (and number if useful) with no grade annotations. Degree framing, including any alternate framing for non-technical roles, comes from the candidate profile. Grad date is "Expected June YYYY" normally, or MM/YY when the posting asks for MM/YY.

- **Section order and headings:** Education, then **Skills (placed near the top, right after Education)** per common career-guide technical-role guidance, then clear experience sections as needed, followed by Leadership if relevant. Preferred defaults are **Professional Experience** (or **Work History**) for employment, **Projects** for named builds, and **Research** for research roles. Tailored headings such as **Relevant Experience**, **Research Experience**, **Engineering Experience**, **Technical Experience**, **Project Experience**, or **AI & Machine Learning Experience** are allowed when they organize the evidence more accurately for the target role. A recognizable, truthful tailored heading is not an ATS failure. Keep headings plain-text and concise, and keep each section reverse-chronological.

- **Professional Experience precedes Projects by default when both appear.** Use projects-first only when role-specific evidence clearly warrants it and the user approves the exception.

- **Skills section:** **bold the category label** (e.g., **Analytical:**, **Technical:**, **Languages:**) followed by a terse, comma-separated keyword list. No full phrases or sentences in the skills section; keywords and proficiencies only. **No rendered Skills line may contain only one word, whether it is a wrapped continuation or a stranded category label.** Rebalance categories or shorten the wording until every Skills line has at least two words; `cv/verify_resume_layout.py` hard-blocks violations. **Languages line:** print it whenever a language the user speaks is plausibly valuable to that employer, not only when the posting names it. **Valuable** covers significant operations in that language's markets, a supplier or manufacturing base there, global or international scope written into the role, a bilingual customer or user base, or localization work. Omit it only when it would be decorative, meaning a purely domestic role with no international surface. Render it **inside the Skills section as its own bold category label**, `Languages: <language> (<proficiency>), <language> (<proficiency>)`, never as a line in the Education block. When a fourth category pushes Skills past the 6-rendered-line ceiling, shorten another category rather than moving Languages back to Education. **On a structured form with a Languages section, fill it in. Pick the ILR-style rung that matches the profile exactly, and do not round it up.**

- **Role lines:** bold title, then ` | `, then italic subtitle/position, then a right-aligned tab to the date. Right tab stop at 10440 twips. Every role header, including organization, position, and date, must render on one physical line. Shorten the organization label if needed. A wrapped role header is a hard Gate B failure enforced by `cv/verify_resume_layout.py`.

- **Bullets:** use a real bulleted list, paragraph style `Normal` (not Word's inherited `List Paragraph` style), solid-circle marker `●` in Times New Roman at the 11pt body size, explicit tab suffix and 720-twip tab stop, and indent left 720 / hanging 360 in both the numbering level and the bullet paragraph. Dedicated symbol fonts are forbidden because they can inflate the rendered line box. Do not substitute the smaller `•` marker; the smaller marker and the wrong paragraph style are what break first-line/wrapped-line alignment in Word and Quick Look. **Every experience must have 2-5 bullets, never 1. This applies to EVERY section including Research and Leadership; no entry anywhere in the document may have a single bullet. A one-bullet entry is a hard Gate B failure, even for an older role. Choose bullet count from posting relevance and evidence strength, never role age.** Each bullet is one sentence or clause, never two sentences joined by an internal full stop. **A bullet may render at most 2 lines at production margins, and most bullets should render 1 line. Cut words or split the bullet, never squeeze spacing; `cv/verify_resume_layout.py` blocks 3-line bullets.** Bullets are fragments with **no trailing period** (matches standard career-guide example bullets); apply this consistently across the whole document. **Every bullet must use the Google X-Y-Z shape:** lead with the result or accomplishment (X), prove it with the strongest honest measure or concrete evidence (Y), then name the method (Z). Prefer numbers. When no valid number exists, use a verifiable artifact or external proof such as an OTLP trace, user test, shipped feature, publication, award, design review, selected cohort, or customer outcome. Never invent a metric to satisfy the formula. Maximize specific proper nouns when true and relevant, including technologies, frameworks, platforms, workflows, datasets, methods, clients, institutions, and awards.

- **Do not combine unrelated projects to save space or evade the 2-bullet minimum.** A shared entry is permitted only when the projects form one genuine, established program block, such as a genuine multi-event program block, and the heading, role, and date range accurately describe every included project. Otherwise, select the strongest relevant project or give each project its own 2-5 bullet entry. If the page cannot hold separate entries, cut the weaker project. A verifier counting two bullets under a combined heading does not make two unrelated one-bullet projects acceptable. This is a hard Gate B failure.
  - **Downstream-impact floor:** an analysis output is not an impact. A bullet that stops at `identified`, `analyzed`, `researched`, `assessed`, `evaluated`, `reviewed`, `conducted`, `explored`, or `investigated` fails unless it states what changed afterward, such as a decision, adoption, launch, allocation, user result, time reduction, cost reduction, revenue effect, or external recognition. This applies especially to the first bullet of the first role. `cv/verify_resume_layout.py` blocks these weak analysis leads when no downstream consequence appears.
  - **X-Y-Z clarification:** X-Y-Z just means **did X, as measured by Y, achieved Z**. A good bullet contains all three, in whatever order reads best. Do NOT force a rigid "[result] by [method]" template or treat any one sample resume as the canonical shape. **For engineering bullets specifically, load them with VERY specific proper nouns: technologies, frameworks, libraries, tools, platforms, datasets, methods. The more concrete proper nouns (when true), the better.** That specificity is what makes an engineer's bullet strong, alongside the measure.

- **Honors/awards:** default to folding a distinction into the experience, project, education entry, or activity that earned it. A compact standalone **Honors**, **Awards**, or **Honors & Awards** section is allowed when a small number of unusually strong, role-relevant distinctions materially strengthens the page and placing them elsewhere would hide or distort them. Do not duplicate an award in both places. The Gate B review must state whether a standalone section was used and why it earned the space.
  - **Default to the earning experience or Leadership entry, with the award written as an outcome of the role. Omit the award if that full entry does not earn its space. Do not use either exception format unless the user explicitly approves it for that specific resume.
  - **⚠️ ONLY TWO FORMATS ARE PERMITTED, and needing space is NOT a justification for a standalone section.** Either (a) a short `Honors:` line inside the Education block under GPA, or (b) a bottom Awards section formatted exactly like every other entry: a real bulleted list, one award per bullet, year right-aligned via the standard tab. **Never invent a third format**, and never let an experience entry masquerade as an award line: compressing a whole leadership entry onto one "honors" line to save space is exactly the distortion this rule forbids.

- **🚨 WHEN THE PAGE WILL NOT FIT, CUT CONTENT OR CUT AN ENTRY.** Do not invent a section format, compress an entry into a line, drop a required check, or leave a known weakness in place because fixing it costs lines. Shortcuts taken to make content fit one page get rationalized afterward, and they are the reason this rule exists. Word-trimming stops working once every bullet renders at exactly 2 lines; past that point the only honest lever is removing a bullet or an entry. The federal exception under Deliverables is the only case where the limit is two pages rather than one, and this rule applies to that limit the same way.

- **Spacing:** body, role, education, and skills paragraphs remain single-spaced (line 240 auto) with paragraph spacing after 0 and before 0. **Section headers carry 8pt (160 twips) before and 2pt (40 twips) after the bottom rule. Bullet text keeps the slightly looser 1.04 line spacing (line 250 auto); ordinary bullets carry 1pt (20 twips) after; and the final bullet of each position, project, research entry, or leadership entry carries 6pt (120 twips) after it to separate entries.** Set the entry-separation space on the final bullet itself; `cv/build_epsilon_lib.js` exposes it as `bullet(text, { final: true })` and every builder must mark the last bullet of each entry. Do not add blank paragraphs. `cv/verify_resume_layout.py` enforces these exact values and blocks bullets that render more than 2 lines. Expect a full resume to give up roughly 2-4 bullets of content; cut by the Relevance-Weighted Cutting rules rather than squeezing spacing back down.
  - **Why these values.** A page with tight section, entry, and bullet boundaries reads as cramped. The fix is white space at those boundaries plus a 2-rendered-line bullet cap, not layout changes: the centered header, the one-line role headers, and all content rules stay.
  - **Do not fix density by cutting content that the page has room for.** Check spacing first, then the bottom-margin spec, then trim. Reducing bullets while an inch of page sits empty is the wrong lever, and it is the failure mode this rule exists to prevent.
  - **A spacing change applies going forward, not retroactively.** Every production `.docx` and PDF of record keeps the spacing it shipped with, so its hash in the tracker still matches. Do not bulk-rebuild old resumes; a document picks up new spacing only when that role is worked again.
  - **Recheck pagination whenever an older resume adopts new spacing.** Do not assume the net change from line count alone; render and verify the exact page.

- **Margins:** 0.6in left/right, 0.45in top/bottom. US Letter. **Cover letters use these exact same margins as the resume; do not widen them.**

- **Cover letters share the resume's header exactly:** centered name (20pt) and centered contact line (11pt, canonical order leading with "<City, ST>"), followed by the **thin black horizontal rule** under the header (the same bottom-border rule the resume uses). This rule must always be present on cover letters, not just resumes.

- **No color** (except standard hyperlink blue), no tables, no text boxes, no multi-column layout (ATS-safe), no template look.

- **Never put a project or repository link in resume or cover-letter body text.** This bans both clickable hyperlinks and printed URLs in every project title, role line, bullet, and cover-letter sentence. Keep only the general GitHub profile in the standard header. A portal's dedicated Website, Portfolio, GitHub, or code-sample field is separate and may receive the appropriate approved link. Treat any employer request for a representative code sample as a separate artifact: review the exact sample with the user and obtain explicit approval before sharing it. The resume verifier must fail any URL detected inside a bullet.

- **Build-environment bullet note:** `Noto Sans Symbols` is not a valid resume marker font in this environment. LibreOffice can fall back to DejaVu Sans or OpenSymbol and enlarge the marker's line box, producing oversized or visibly double-spaced bullets. Set the numbering marker run to Times New Roman at the 11pt body size. Do not use a dedicated symbol font, shrink the marker, or switch to the smaller `•`. The exact-pair verifier now blocks dedicated symbol fonts in both DOCX OOXML and rendered PDF output, but the page PNG must still be inspected at 100% zoom.

- Keep exactly one builder under `cv/` as the current visual authority and name it here; label its output DO NOT SUBMIT when it exists only to demonstrate format. A builder that predates a spacing change is no longer the authority, and the content-bank generator under `cv/build_master.js` is not the visual authority either. New builders must use the bundled workspace dependency path and write with `path.join(__dirname, ...)` so the canonical output always lands under `cv/` regardless of shell working directory.

- **PDF is the visual authority:** DOCX layout can vary across Microsoft Word, Finder Quick Look, and LibreOffice. Keep the DOCX as the editable source, but use the rendered PDF for the user's review and for submission whenever the portal accepts PDF. Do not ask the user to approve layout from a DOCX preview, and do not upload a DOCX when PDF is accepted. The PDF the user reviews must be the exact PDF later uploaded.

- **Role lines:** bold title, then ` | `, then italic subtitle/position, then a **separate tab run** followed by a regular date run. The tab is right-aligned at 10440 twips. Do not concatenate the tab and date into one text run. Every role header, including organization, position, and date, must render on one physical line. Every rendered date must end at the same right edge; shorten the organization label if a long role line would wrap or displace the date. A wrapped role header is a hard Gate B failure enforced by `cv/verify_resume_layout.py`.

- **Bullets:** use a real bulleted list with paragraph style `Normal`, solid-circle marker `●`, marker font **Times New Roman at the 11pt body size**, explicit tab suffix and 720-twip tab stop, and indent left 720 / hanging 360 in both the numbering level and bullet paragraph. A dedicated symbol font, including Noto Sans Symbols, DejaVu Sans, or OpenSymbol, is forbidden because LibreOffice can enlarge its line box and make single-spaced bullets render as double-spaced. Do not substitute the smaller `•` marker. In Finder Quick Look and the rendered PDF, every continuation line must start at exactly the same x-position as the first line's text. **Every experience must have 2-5 bullets, never 1. This applies to EVERY section including Research and Leadership; no entry anywhere in the document may have a single bullet. A one-bullet entry is a hard Gate B failure, even for an older role. Choose bullet count from posting relevance and evidence strength, never role age.** Each bullet is one sentence or clause, never two sentences joined by an internal full stop. **A bullet may render at most 2 lines at production margins, and most bullets should render 1 line. Cut words or split the bullet, never squeeze spacing; `cv/verify_resume_layout.py` blocks 3-line bullets.** Bullets are fragments with **no trailing period** (matches standard career-guide example bullets); apply this consistently across the whole document. **Every bullet must use the Google X-Y-Z shape:** lead with the result or accomplishment (X), prove it with the strongest honest measure or concrete evidence (Y), then name the method (Z). Prefer numbers. When no valid number exists, use a verifiable artifact or external proof such as an OTLP trace, user test, shipped feature, publication, award, design review, selected cohort, or customer outcome. Never invent a metric to satisfy the formula. Maximize specific proper nouns when true and relevant, including technologies, frameworks, platforms, workflows, datasets, methods, clients, institutions, and awards.


## How to build and check the `.docx` (concrete commands)
The current formatting authority is whichever builder this file names above, not an older tailored builder. `cv/build_master.js` is the content-bank generator and is held to the same spacing, marker-font, style, and output-path rules, but it is not a substitute for comparing the exact render against a current approved resume.

1. **Write the build script.** Copy the layout pattern from the current authority builder and the shared helpers in `cv/build_epsilon_lib.js` to `cv/build_<company>.js`, swap in the selected roles/bullets, and set the output with `path.join(__dirname, "<Your Name> - <Company>.docx")`. A builder that writes relative to the shell working directory is a blocking failure because it can create a root-level duplicate while stale files remain under `cv/`.
2. **Build it.** From the repo root:
   ```
   cd cv
   npm install docx      # only if cv/node_modules/docx is missing
   node build_<company>.js
   ```
3. **Convert to PDF for review and submission** (LibreOffice is the converter; `soffice` must be installed on the machine):
   ```
   soffice --headless --convert-to pdf --outdir cv "cv/<Your Name> - <Company>.docx"
   ```
   If `soffice`/`libreoffice` is not installed, say so and ask the user to open the `.docx` and confirm it is one page (two under the federal exception), rather than guessing.
4. **Verify programmatically and visually** (see `11-verification-checklist.md`). Render the canonical `cv/*.docx` into a fresh task-local directory, copy that exact PDF to the matching `cv/*.pdf`, and run `cv/verify_resume_layout.py <rendered.pdf> --docx <source.docx>` on the canonical pair. The verifier blocks mismatched names or directories, a PDF older than its DOCX, normalized PDF text that differs from the DOCX source, paragraph or line spacing outside the approved 240-twip body and 250-twip bullet rules, section or role spacing above the approved maximum, a dedicated bullet symbol font, or incorrect marker geometry. Also check page count with `pdfinfo`, inspect embedded font families and Unicode mappings with `pdffonts`, and dump text with both `pdftotext -layout` and `pdftotext -raw`. Render the PDF to a full-page PNG and inspect it at 100% zoom. Compare it side by side with a current approved resume PDF. The comparison must explicitly cover bottom-page density, solid-circle bullet marker, first-line and wrapped-line alignment, role/date separation, common right edge for every date, section spacing, and page margins. Present only the verified canonical PDF to the user for review. Treat DOCX/Quick Look differences as source-editor variance, not as the submission layout, unless a portal requires DOCX.
